```dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# System deps (as root) — curl for HEALTHCHECK, node for CLI backends.
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl nodejs npm \
    && rm -rf /var/lib/apt/lists/*

RUN npm install -g @openai/codex@latest @google/gemini-cli@latest

# Create non-root user BEFORE COPY so --chown can land in a single layer.
RUN groupadd --system --gid 1000 appuser \
    && useradd --system --uid 1000 --gid appuser --home-dir /home/appuser --create-home appuser

# DOCK-03: deps layer cached separately from app code.
COPY --chown=appuser:appuser requirements.txt /app/requirements.txt
RUN pip install --no-cache-dir -r /app/requirements.txt

# App code last (cache miss here doesn't re-run pip install).
COPY --chown=appuser:appuser . /app
RUN chmod +x /app/docker-entrypoint.sh \
    && mkdir -p /data \
    && chown -R appuser:appuser /data /app

USER appuser

EXPOSE 5000

HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
    CMD curl -fsS http://localhost:5000/api/health || exit 1

CMD ["/app/docker-entrypoint.sh"]
```

- `HEALTHCHECK` uses `start-period=15s` to let Alembic migrations run on cold boot without flapping to unhealthy (Pitfall P-06).
- `groupadd` + `useradd` use `--system` + `--uid 1000` to pin UID (Pattern 6 rationale).
- Node modules installed globally via npm (line 12 equivalent) are world-readable in `/usr/lib/node_modules`, so relocating HOME does not break the CLI binaries themselves — only their config path changes.
- Do NOT move `COPY docker-entrypoint.sh` as a separate line; the single `COPY --chown=appuser:appuser . /app` already includes it. Keep the `chmod +x` line.

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host filesystem → container (bind mounts) | `${HOME}/.codex` and `${HOME}/.gemini` mounted read-write into the container. Anything the container writes to these paths modifies the developer's host home directory. |
| Container network → host network | Port `5050:5000` exposes Flask on the host; the healthcheck runs INSIDE the container on `localhost:5000` (container-internal), so external port mapping is not part of the health-probe attack surface. |
| Container process → /data (named volume) | SQLite DB holds settings including `telegram_token`, `llm_api_key`, and other secrets. The named volume is container-owned and isolated from the host unless explicitly mounted; still UID-1000-readable inside the container. |
| Host env → container env (SECRET_KEY, TELEGRAM_BOT_TOKEN) | Secrets crossing via docker-compose env vars. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-03-01 | Elevation of Privilege | Container escape from the Flask process to host root (previous `USER root` default) | mitigate | `USER appuser` (UID 1000) — even on kernel/runtime escape, attacker lands as unprivileged UID 1000. Combined with Docker's default capability drop this closes the common escape-to-root path. |
| T-05-03-02 | Tampering | `/data/docksentinel.db` corruption / unauthorized write by a rogue container on the same Docker host | mitigate | Named volume `docksentinel_data` is owned by the container's UID on first creation — other containers without the volume mount cannot reach it. Do NOT grant `--privileged`. |
| T-05-03-03 | Information Disclosure | `SECRET_KEY`, `TELEGRAM_BOT_TOKEN`, `LLM_API_KEY` secrets in `docker compose config` output | mitigate | `SECRET_KEY=${SECRET_KEY:?...}` requires the var to be set externally (not baked into compose). Never echo these via `printenv` or `docker inspect --format='{{.Config.Env}}'` in HEALTHCHECK or entrypoint. Preserve the existing `:?` required-var syntax. |
| T-05-03-04 | Information Disclosure | `docker exec docksentinel env` revealing LLM API keys | accept | Any user with `docker exec` already has shell on the container; the DockSentinel trust model assumes Docker daemon access is root-equivalent on the host. Out of scope to further harden. |
| T-05-03-05 | Tampering | Host `${HOME}/.codex` and `${HOME}/.gemini` bind mounts allowing the container to modify the developer's LLM CLI config | mitigate (by design) | Required for the CLI backends to function. The container reads/writes its own config files under these paths — same semantics as running the CLI on the host. If the operator uses this in a shared/CI context, they MUST use a per-container dummy HOME (document in summary). |
| T-05-03-06 | Denial of Service | Healthcheck triggers before Alembic migrations complete on cold boot, container flaps | mitigate | `start_period=15s` + `retries=3` at `interval=30s` — gives 15s of "not counted" failures plus 3 full cycles before the orchestrator marks unhealthy. Pitfall P-06. |
| T-05-03-07 | Denial of Service | Attacker floods `/api/health` to exhaust the Flask worker pool | accept | `/api/health` returns quickly (reads a cached `SentinelState.singleton()`). DockSentinel is a single-tenant tool on an internal/local network; rate-limiting is out of scope. |
| T-05-03-08 | Tampering | `curl` used by HEALTHCHECK pulled from a compromised apt cache | mitigate | `apt-get install curl` runs against the official `python:3.12-slim` base image's Debian apt sources, which are TLS-verified by default. The image SHA is pinned at build time. If concerned, pin base image by digest in a follow-up. |
| T-05-03-09 | Tampering | Npm packages `@openai/codex` / `@google/gemini-cli` using `@latest` — supply-chain risk (version drift between builds) | accept | Existing behavior (already `@latest` in the pre-Phase-5 Dockerfile). Pinning these is a follow-up; not in scope for DOCK-01..04. |

</threat_model>
